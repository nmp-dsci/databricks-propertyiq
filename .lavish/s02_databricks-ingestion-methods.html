Every way to get data into Databricks — and which one you actually built

Your framing was “Parquet → declarative pipeline”. The Parquet half is right. The second half is not: this project uses Auto Loader inside a Lakeflow Job notebook task, which is a different product from Lakeflow Declarative Pipelines. That distinction is exactly the kind of thing an SA panel probes, so section 00 fixes it first — then the rest of the page maps the full option space and drills you on the tradeoffs, using your own pipeline as the worked example.

00 The correction, stated plainly

Get this right in the room. Auto Loader is a source. Declarative Pipelines is a framework. You can use either without the other, and you used one of them.

Auto Loader you use this

A Structured Streaming source (format("cloudFiles")) that incrementally discovers new files in object storage and tracks them exactly-once in a checkpoint. It is a reader. It has no opinion about where it runs.

Lakeflow Jobs you use this

The general-purpose orchestrator: a DAG of tasks (notebooks, SQL, Python wheels), each running arbitrary code. Your four tasks — bronze, silver, gold, checks — are notebook tasks in a job.

Declarative Pipelines you don't

Formerly Delta Live Tables, now Lakeflow Declarative Pipelines. You declare tables and their queries; the framework infers the DAG, manages checkpoints, applies EXPECTATIONS, and handles incremental refresh. You never write writeStream.

The one-line answer if asked. “I used Auto Loader for bronze ingestion, orchestrated as notebook tasks in a Lakeflow Job rather than a Declarative Pipeline — because the transform logic is a plain unit-tested Python library and I wanted explicit control over the silver rebuild semantics. I hand-rolled the two things DLT would have given me for free: expectations, as a _quality array plus a checks task, and orchestration, as a four-task DAG.”

That answer is strong because it names what you gave up. Section 06 is the full version.

Three properties of this design are worth being able to defend on their own, because each was a deliberate choice with a rejected alternative behind it:

Landing is append-only

A rewritten partition arrives as a new file beside the old one, keyed by content hash. This is not a stylistic preference — Auto Loader tracks files exactly-once and never re-reads a file whose contents changed. Overwriting in place would silently drop the update.

The schema is declared, not inferred

Every column STRING, matching the publisher's contract, with schemaEvolutionMode = "rescue". Unexpected fields land in _rescued_data rather than failing the run or flipping a column's type between runs.

Checkpoints are versioned in their name

FEED_VERSION = "v2_parquet". A checkpoint carries the file list and schema of the feed it was built against. When the feed changed from CSV to Parquet, reusing it would have made Auto Loader skip every new file. A new suffix forces a clean re-ingest.

It is not created per run — see below.

When is the checkpoint created? Not when the job starts.

This is the misconception worth killing early, because the whole exactly-once story depends on it. The checkpoint is written once, on the first run of that stream, into a durable path you chose — here a Unity Catalog volume. Every run after that opens the existing checkpoint and appends to it. It is persistent storage that outlives the job, not per-run scratch: the compute is ephemeral, the checkpoint is not. That asymmetry is the entire point — a fresh cluster with no memory of anything still knows exactly which 760 files it has already read.

What is actually on disk right now

_pipeline/checkpoints/bronze_sales_v2_parquet/
├── offsets/      0, 1     # batch about to run
├── commits/      0, 1     # batch that finished
├── metadata/              # stream id
└── sources/0/
    ├── rocksdb/           # the seen-files store
    ├── listing_stats
    └── metadata

_pipeline/schemas/bronze_sales_v2_parquet/
└── _schemas/              # schemaLocation, separate

Batches 0 and 1, not 0 alone. That numbering is the proof: it is monotonic across runs. Run one wrote batch 0; a later run found new files and wrote batch 1 into the same checkpoint. A per-run checkpoint would restart at 0 every time — and would reprocess all 3.1 M rows every time.

The write-ahead protocol, and why it's exactly-once

Each batch writes offsets/N before doing the work and commits/N after. If the run dies in between, the next run sees an offset with no matching commit and replays that batch — combined with an idempotent Delta write, that is the exactly-once guarantee.

The seen-files list lives in RocksDB under sources/0/, which is what Auto Loader consults to decide a file is new. It is keyed by path — which is precisely why a file mutated in place is invisible to it, and why landing had to become append-only.

schemaLocation is a separate path from checkpointLocation. Both are versioned with FEED_VERSION here, so a feed change resets both together.

The interview trap in this. Because the checkpoint is durable and per-stream, deleting it is a full reprocess and pointing a new feed at an old one is a silent skip. Both are real outages; neither throws an error. And two concurrent streams writing one checkpoint corrupts it — which is exactly why the double-armed file_arrival trigger in section 07 mattered.

That third one is your best war story. It is a real, non-obvious failure mode that most candidates have never hit, and the fix is one line. Have it ready.

The four questions behind every branch

1. Shape — files, rows in a database, events on a bus, or an API? 2. Latency — is the honest requirement seconds, minutes, or “by the morning”? 3. Ownership — who maintains this in eighteen months? 4. Governance — does it need UC lineage and access control from the first hop?

The trap in most scenarios

Candidates reach for streaming because it sounds sophisticated. Latency requirements are almost always softer than stated, and streaming costs real operational complexity. Ask what decision the freshness enables before designing for it — that question alone reads as senior.

04 Auto Loader, in the detail you'll be drilled on

stream = (
    spark.readStream.format("cloudFiles")
    .option("cloudFiles.format", "parquet")

)
(stream.writeStream.format("delta")
    .option("checkpointLocation", f"{state_root}/checkpoints/bronze_{name}_{FEED_VERSION}")

File discovery: listing vs notification

Auto Loader finds new files either by directory listing (default; simple, no cloud setup) or via file notification / file events (a queue fed by storage events; scales to millions of files and avoids listing cost).

Here, 875 files across two directories — listing is entirely adequate. The scale answer: “at millions of files per day, directory listing becomes the bottleneck and I'd move to file notification mode.” Knowing the switch exists is what's being tested.

Trigger modes, and why availableNow

Three options: continuous (always on, lowest latency, always billing), processing time (micro-batch every n seconds), and availableNow — process everything currently available, then terminate.

availableNow gives you streaming's exactly-once file tracking on a batch cost profile. For a feed that publishes weekly, paying for an always-on stream would be indefensible.

The checkpoint is the whole story

It holds the file list processed so far and the inferred schema. Consequences: delete it and you reprocess everything; point it at a changed feed and Auto Loader skips the new files; run two streams against one checkpoint and you corrupt it.

Hence FEED_VERSION in the path. This is the detail that separates having read the docs from having run it.

Schema evolution modes

addNewColumns (default — fail the run, add the column, succeed on retry), rescue (park unknowns in _rescued_data, never fail), failOnNewColumns, and none.

rescue was chosen here because bronze must be lossless and unattended: an upstream column addition should never break a run, but it must not vanish either.

The gotcha worth volunteering. Auto Loader tracks files by path and never re-reads one it has already seen — so a feed that mutates files in place is silently, permanently broken. Rentboard rewrites its trailing month every run. The fix is upstream: name each file <partition>_<sha8>.parquet so a rewrite lands as a new file, then have silver's resolve_versions() pick the newest per partition with a window function.

That is a genuine architecture answer — the ingestion constraint propagated back into the file naming contract of a different repository. Interviewers remember that shape of story.

When this is the right call

The bus already exists and serves other consumers with real-time needs. The lakehouse is the analytical consumer, and analytics does not need sub-second data. You get decoupling, unbounded replay from files, and no always-on Databricks compute — while the operational consumers keep their latency.

That's a legitimate and often optimal architecture. Say so.

When it's a smell

If the lakehouse is the only consumer, the bus is buying nothing and costing plenty — you've paid for streaming infrastructure and then reintroduced batch latency at the sink anyway. The sink's flush interval becomes your real latency floor, and people are often surprised to learn their “real-time pipeline” is a 5-minute one.

Also watch the classic sink failure: many tiny files. Great for latency, poor for scan performance.

The question that reframes the whole thing. “What decision gets made on this data, and how fast?” If a human looks at a dashboard each morning, minutes and seconds are indistinguishable and you have just spent an on-call rotation on nothing. If an automated system acts within seconds — fraud holds, routing, alerting — then streaming is justified and you build shape B.

For PropertyIQ the source publishes weekly. Streaming would be architecture theatre, and saying that plainly is stronger than pretending otherwise.

06 Job + Auto Loader vs Declarative Pipelines

The comparison your framing implied you'd already made. Make it explicitly, and own the tradeoff.

Job + notebook tasks what you built

Four notebook tasks in sequence on serverless, importing a pure Python transform library.

  • 5-second local test loop. src/lib/transforms.py is pure DataFrame→DataFrame, unit-tested against local Spark with no workspace at all.
  • Explicit rebuild semantics. Silver and gold are deliberate full .mode("overwrite") recomputes — idempotent and self-healing on restated partitions.
  • Custom dedup. resolve_versions() is a window function over landed partitions. Expressible in LDP, but you own it outright here.
  • Quality kept, not dropped. Invalid rows survive into silver with a _quality array, so the quality dashboard and the price dashboard read the same table.

cost: you hand-rolled orchestration, expectations and the checks task

Lakeflow Declarative Pipelines the alternative

Declare bronze/silver/gold as streaming tables and materialised views; the framework does the rest.

  • Expectations built in. @dp.expect_or_drop and friends replace most of the 04-checks notebook, with quality metrics in the pipeline UI for free. (Note dp, not dlt — from pyspark import pipelines as dp is the modern API; import dlt is legacy and still parses.)
  • No checkpoint management. The FEED_VERSION problem largely disappears — the framework owns stream state.
  • Automatic lineage and DAG inference. No depends_on written by hand.
  • Incremental for free. Streaming tables and AUTO CDC give you the incremental silver you explicitly chose not to build.

cost: logic lives in the framework, so the fast local unit-test loop gets much harder

How to land this in the room. “For a portfolio pipeline where the transform rules are ported from tested dbt models, I wanted them as a unit-tested library, so a job was the better fit. For a production team pipeline I'd default to Declarative Pipelines — expectations and managed checkpoints are worth more than the local test loop once more than one person owns it.”

Having a real reason to not use the flagship product, plus a clear condition under which you'd switch, beats having used it without thinking.

Also expect: “why not incremental silver and gold?” You measured it — a full rebuild is 77 seconds (silver 51, gold 26), so that is the entire ceiling on the saving. And the trap is specific: a sales partition is a publication week, but its contract dates scatter across many months, so “which months changed” cannot be read off the filename — it has to come from the batch's data. Idempotency for 77 seconds was the right trade, and it gets revisited when the rebuild stops fitting the run window.

08 Q&A drill

Likely questions, with answers grounded in things you actually did. Open each and say it out loud — that's the part that matters.

Walk me through how you'd ingest a daily drop of Parquet files into the lakehouse.

Land them in a Unity Catalog volume or external location, then Auto Loader with cloudFiles.format = parquet and trigger(availableNow=True) writing append-only into bronze. Directory listing is fine to start; file notification mode if volume grows. Declare the schema rather than infer it, with schemaEvolutionMode = "rescue" so unexpected columns are captured rather than dropped or fatal. Trigger the job on file arrival rather than a schedule, so the run tracks the publish instead of the clock.

Then the medallion split: bronze lossless, silver typed and quality-flagged, gold aggregated for the BI layer.

When would you use COPY INTO instead of Auto Loader?

A bounded, one-off or low-frequency SQL-native load — a backfill, a reference dataset, a few thousand files — where idempotent retry is all you need and you don't want to own a checkpoint. Databricks itself recommends streaming tables over COPY INTO for anything that needs to scale, so I treat it as the simple-case tool rather than the default.

What breaks if the upstream system overwrites a file in place?

Auto Loader tracks files exactly-once by path and never re-reads one it has processed, so the update is silently and permanently lost. There's no error — which is what makes it dangerous.

I hit exactly this: the rental bond feed rewrites its trailing month on every run. The fix was to make landing append-only by putting a content hash in the filename, so a rewrite arrives as a new file, and to have silver resolve the newest version per partition with a window function. The ingestion constraint became a naming contract in the upstream repo.

Why didn't you use Declarative Pipelines?

Because the transform rules were a port of tested dbt models, and I wanted them as a pure Python library with a five-second local test loop rather than logic embedded in a framework. I also wanted explicit control over the silver rebuild, which is a deliberate full overwrite for idempotency.

What I gave up is real: expectations, managed checkpoints, DAG inference and lineage. I hand-rolled the first two as a _quality array and a dedicated checks task. For a production pipeline with more than one owner I'd default to Declarative Pipelines.

How do you handle schema drift?

Declare the schema at the boundary so it's a contract rather than a guess, and set schemaEvolutionMode deliberately. Here it's rescue: bronze must be lossless and unattended, so a new upstream column lands in _rescued_data instead of either failing the run or disappearing. Then it's a visible, deliberate decision to promote it into silver.

The alternative, addNewColumns, fails the stream and restarts with the column added — better when you want a human to notice immediately.

Batch or streaming — how do you decide?

I start by asking what decision the freshness enables. Stated latency requirements are usually softer than the real ones, and streaming buys genuine operational complexity: offsets, watermarks, late data, state.

availableNow is the answer I reach for most: streaming's exactly-once semantics and checkpointing, on a batch cost profile. You only need true continuous streaming when something acts on the data in seconds.

The source is Salesforce, not files. What changes?

Lakeflow Connect has a managed Salesforce connector — serverless, incremental, UC-governed — so I wouldn't build an integration. Same for Workday, HubSpot, Jira, ServiceNow, and CDC connectors for SQL Server, Postgres and MySQL. Only if no connector existed would I fall back to a partner ELT tool or an extract-to-files pattern, which puts me back on Auto Loader.

Everything downstream of bronze is unchanged — that's the point of the medallion boundary.

What would you do differently at 100× the volume?
  • Auto Loader to file notification / file events — directory listing becomes the bottleneck.
  • Silver and gold to incremental — full recompute is right at 77 seconds, wrong when it stops fitting the run window.
  • Move to Declarative Pipelines for managed checkpoints and expectations once more than one person owns it.
  • Liquid clustering on the big silver tables rather than static partitioning.
  • Separate the bronze ingest from the transform DAG so a slow rebuild can't delay landing.
Anything you got wrong?

Two, both worth telling. First: serverless SQL runs in ANSI mode, where casts and to_date throw on malformed input, while the local Spark in my unit tests silently returned NULL for the same value. The real data contains a genuine 6-digit date. Green tests, failing job. Fixed with try_to_timestamp and regex-guarded casts, plus a fixture covering it.

Second: the two-armed-triggers bug in section 07 — mode: production doesn't auto-pause triggers the way development does.
