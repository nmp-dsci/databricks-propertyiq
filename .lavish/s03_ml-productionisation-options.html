The Production AI Playbook — Databricks

Doctrine that anchors the design: deploy code, not models (the training pipeline is the deployable; each environment retrains and registers its own version), Unity Catalog is the spine (data → features → model → inference table → metrics all governed and lineage-linked), and evaluation gates before promotion — the interview corpus is explicit that generic answers "lacking Databricks-specific depth" fail.

The rubric — 8 things a production ML story must demonstrate

This is a project commitment, not a menu: the end state of the ml-task branch is that this repo demonstrates every row below — the full loop, live in the workspace. The options are the vehicles that get there; the phased plan at the bottom maps each rubric row to the concrete repo artifact that closes it.

R1 Reproducible training as code

Training is a bundle-deployed job, not a notebook someone ran once. Logic lives in unit-tested library code; "deploy code, not models" — each environment retrains from the same source.

here → training pipeline in src/lib/ml/, tested by make test, deployed by the existing DAB alongside the medallion job.

R2 Experiment tracking & lineage

Every run logs params, metrics, artifacts and data lineage. MLflow 3 idiom: log_model(name=…), LoggedModel entity, UC lineage from gold table → model version.

here → MLflow experiment per option; input_example + signature logged; lineage visible in Catalog Explorer.

R3 Registry, aliases & promotion gates

Models registered in Unity Catalog (catalog.schema.model). Stages are gone — @champion/@challenger aliases plus an evaluation gate (MLflow 3 deployment job: evaluate → approval → alias flip) guard promotion.

here → challenger only takes @champion when it beats the incumbent on a held-out window; approval task = human-in-the-loop.

R4 Feature engineering without skew

Features come from a governed UC feature table (primary key + timeseries column, point-in-time lookup) so training and inference read identical logic — no train/serve skew.

here → propertyiq_ml.features_* feature table built from gold marts by the same tested transforms.

R5 Inference at the right latency

Batch by default (mlflow.pyfunc.spark_udf in a scheduled job); real-time only when the use case needs it (serverless CPU endpoint, ai_query() from SQL). Knowing which — and why — is the SA question.

here → Option A is batch, Option C is a live endpoint; the artifact of each is a queryable predictions surface.

R6 Monitoring, drift → retraining

Predictions and inputs land in tables; drift/quality metrics are computed on a schedule; a threshold breach triggers retraining (condition task), not a human noticing a bad dashboard.

here → hand-rolled drift-metrics table + SQL alert (Lakehouse Monitoring on Free Edition is unverified — saying so is part of the story).

R7 Governance & auditability

UC owns permissions, comments and lineage end-to-end; model versions carry descriptions; predictions tables document their model version so any number is traceable to code + data.

here → every scored row carries model_version + scored_at; comments written for Genie, same as the gold marts.

R8 CI/CD for ML

MLOps Stacks shape: bundle-validated resources, unit tests in CI, PR-gated. Training + scoring jobs are resources in the same DAB as the data pipeline.

here → extend resources/jobs/ with ml_train.yml + ml_score.yml; existing GitHub Actions already lints/tests/validates.

How it works — from coding agent to running on Databricks

The ML work rides the exact same loop the medallion pipeline already uses. Nothing new to learn: the agent writes code in this repo, and the bundle deploy ships the local working tree (committed or not — git is not in the loop; CI only lints, tests and validates).

The inner loop, per phase

  1. Agent writes logic in src/lib/ml_*.py + thin notebooks in src/notebooks/ml/, jobs in resources/jobs/ml_*.yml
  2. make test — feature/model/gate logic proven on local Spark in ~20s, no workspace touched
  3. make deploy — validates the bundle, then uploads the working tree to /Workspace/Users/<you>/.bundle/databricks-propertyiq/dev/files/ and creates/updates the ml_train + ml_score jobs
  4. databricks bundle run ml_train -t dev — runs training on serverless, logs stream to the terminal; the run registers the model and decides the champion
  5. Check the acceptance boxes above (CLI + SQL + UI); iterate — edit locally, deploy, run again

What lands where

  • codemirrored under …/.bundle/…/dev/files/ — the job runs this deployed copy, never your git branch
  • jobs[dev <you>] propertyiq-ml-train / -ml-score in the Jobs UI (dev-mode prefix)
  • modelworkspace.propertyiq_ml.rent_estimator in Unity Catalog, aliases and all
  • tablespropertyiq_ml.features_rent / predictions_rent / drift_metrics
  • endpointPhase 2's serving endpoint, bound to @champion, updated by alias flip alone
  • ciGitHub Actions on push: ruff + pytest + bundle validate — it never deploys; deploys only happen from your machine
One consequence to know: make deploy ships whatever is on disk — including the uncommitted declarative-pipeline files from the earlier comparison work. They create a paused, never-running pipeline; harmless, but expect to see it appear.

The three options

Each is one model taken end-to-end. They are deliberately different shapes — regression, forecasting, real-time serving — because together they cover the whole rubric and the whole "which latency, which tool, why" conversation.

A — Rent regression through the full batch MLOps loop

recommended first lowest platform risk · deepest rubric coverage
The task

Predict median_weekly_rent per postcode × property_type × bedroom_band × month from lagged features off the gold marts (trailing medians, sales volume, yield, month-of-year). LightGBM/sklearn — the model is a vehicle; the loop is the point.

End-to-end path
  1. Feature table propertyiq_ml.features_rent (PK + month timeseries column) built by tested library code
  2. Train on serverless job → MLflow 3 run (params, metrics, signature, input example)
  3. Register to UC → challenger; evaluation gate: time-based backtest must beat @champion MAE on the last 6 held-out months
  4. Winner takes @champion; weekly ml_score job scores next-month grid via spark_udf → predictions_rent table with model_version stamped
  5. Drift job: PSI per feature + rolling MAE once actuals land → metrics table → SQL alert → retrain trigger
  6. All of it as two job YAMLs in the existing bundle; predictions surfaced in the dashboard/Genie
Scorecard
  • provesR1–R4, R6–R8 fully; R5 batch half
  • effort~2–3 sessions; nothing unverified in the path
  • interviewThe direct answer to "how do you get ML to production?" — champion/challenger, gates, drift-triggered retraining, all demoable live
Risk: low. Only soft spot is pinned %pip install lightgbm on Free serverless — fallback is sklearn's HistGradientBoosting (pre-installed, same demo value).
Delivered when — every check passes
  • climake test green (feature + model + gate logic unit-tested locally) and make validate passes with the two new job resources.
  • clidatabricks bundle run ml_train -t dev completes; run log shows the gate verdict ("champion stands" or "promoted vN").
  • clidatabricks registered-models get workspace.propertyiq_ml.rent_estimator returns the model; its aliases list shows champion on the winning version.
  • sqlSELECT * FROM propertyiq_ml.predictions_rent LIMIT 5 returns rows carrying model_version + scored_at; drift_metrics has one PSI row per feature.
  • uiCatalog Explorer → propertyiq_ml shows features_rent (with PK + comment), predictions_rent, drift_metrics; lineage tab links features → model.
  • uiExperiments UI shows the training runs with params/metrics; Models UI shows versions and the @champion alias; Jobs UI shows ml_train and ml_score green.

B — Yield forecasting: platform-native vs hand-rolled, compared

stretch the "two implementations" narrative, again
The task

Forecast gross_yield_pct (or median sale price) 6 months ahead per postcode × property_type. Two implementations of the same task, mirroring this repo's existing job-vs-declarative-pipeline comparison: AI_FORECAST in pure SQL on the warehouse vs a trained per-group model (statsforecast/ETS via applyInPandas) through the same MLflow loop as Option A.

End-to-end path
  1. Probe: does AI_FORECAST run on the Free 2X-Small serverless warehouse? (10-minute test, honest finding either way)
  2. SQL path: AI_FORECAST(TABLE(…), horizon, group_col) → forecast table, scheduled via existing make sql runner
  3. Model path: per-postcode seasonal model trained in parallel with applyInPandas, logged as one pyfunc, registered + gated like Option A
  4. Rolling-origin backtest compares both against a naive baseline — the comparison table is the deliverable
Scorecard
  • provesR1–R3, R5 batch, R8; adds "when do you *not* train a model" judgment
  • effort~2 sessions; AI_FORECAST availability unknown until probed
  • interviewSA-shaped: tool selection + honest trade-off table beats a better model. Time-series eval (no shuffled splits) shows real ML literacy
Risk: medium. AI_FORECAST on Free is unverified — but a documented "not available on Free Edition, here's the paid-tier syntax" is itself a credible SA finding. The trained path has no platform risk.
Delivered when — every check passes
  • sqlThe AI_FORECAST probe result is committed either way: a working query via make sql, or the exact error message documented as the Free Edition finding.
  • clidatabricks bundle run ml_forecast -t dev trains the per-postcode models and completes green.
  • sqlSELECT * FROM propertyiq_ml.forecast_comparison returns the backtest table: MAE per method (trained model, AI_FORECAST if available, naive baseline) per horizon.
  • uiCatalog Explorer shows forecast_rent + forecast_comparison with comments; the comparison README section in the repo states the honest winner.

C — Real-time rent estimator on a serving endpoint

recommended second the "half your conversations" capability
The task

Serve the Option A champion (or a small dedicated rent-estimator) as a serverless CPU Model Serving endpoint: give it postcode, property type, bedrooms → get an estimated weekly rent band, live. Queried three ways: REST, ai_query() from the warehouse, and (optionally) the existing dashboard.

End-to-end path
  1. Serving endpoint as a bundle resource pointing at models:/…@champion — promotion = alias flip, zero endpoint config change
  2. Inference logging on → requests/responses land in an inference table
  3. ai_query() demo from SQL: score ad-hoc rows on the warehouse against the live endpoint
  4. Canary story: champion alias flip after the Option A gate = staged rollout narrative
  5. Endpoint metrics + inference table feed the same monitoring loop
Scorecard
  • provesR5 real-time half, R6 (inference tables), R7; completes R3's story (alias → endpoint)
  • effort~1 session on top of A (it reuses A's model + registry)
  • interviewModel serving is "half of your conversations" per the SA corpus — a live endpoint you can curl during a demo is the strongest artifact here
Risk: medium-low. CPU serving is confirmed on Free Edition but endpoint quota is unpublished; ai_query against custom endpoints on Free is partially unverified. Build after A so the registry story already stands.
Delivered when — every check passes
  • clidatabricks serving-endpoints get propertyiq-rent-estimator reports state READY, config bound to models:/…rent_estimator@champion.
  • clidatabricks serving-endpoints query propertyiq-rent-estimator --json '{…}' returns a live weekly-rent prediction for a sample postcode/type/bedrooms row.
  • sqlai_query('propertyiq-rent-estimator', named_struct(…)) returns the same prediction from the warehouse — or its exact failure is documented as a Free Edition finding.
  • uiServing UI shows the endpoint Ready with request metrics ticking after the demo queries; inference/payload logging visible.
  • uiAfter the next ml_train promotion, the endpoint serves the new version with zero endpoint config change — the alias flip is the deploy.

Decision — all three, phased

decided 2026-08-16  Build all three options on branch ml-task, in rubric-closing order: Phase 1 — A (full batch loop), Phase 2 — C (serving endpoint on A's champion), Phase 3 — B (forecasting comparison). Settled design choices that follow the repo's existing patterns:

  • Schema: new propertyiq_ml schema with its own bundle variable — mirrors the propertyiq_dp pattern, so ML tables can never collide with the marts.
  • Promotion gate: condition task inside ml_train (backtest challenger vs champion, flip alias on a win); the MLflow 3 deployment-job pattern is narrated as the upgrade path.
  • Option A target: median_weekly_rent — dense at the grain, intuitive to demo.
