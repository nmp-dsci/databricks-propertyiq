Why bronze and silver now match exactly. Before the purge, bronze carried both feeds and resolve_versions() in src/lib/transforms.py was the only thing stopping gold from doubling — it keeps only rows whose _source_file matches the <partition>_<sha8>.parquet contract. I used that same contract as the DELETE predicate rather than LIKE '%.csv', so the purge and the filter can never disagree about what counts as a real landing file.

That filter is still load-bearing, just for a different reason now: it also resolves versions, keeping the newest file when a partition gets restated upstream — which rentboard does to its trailing month on every run. Purging the CSV rows did not make it redundant.

Noticed while doing this: six new sales partitions landed and a run picked them up between when I wrote this plan and when I executed it — bronze went 754 → 760 files and gold moved with it. Nothing wrong, but it is a live demonstration of the point in section 05: bronze ingests incrementally, and silver and gold simply rebuild around whatever bronze now holds.

05 Can silver and gold be incremental?

Yes, technically — and my advice is not to, yet. Here is the honest arithmetic rather than an opinion.

What a full rebuild actually costs you: 77 seconds. Silver takes 51 s and gold 26 s on the last successful run. Even a perfect incremental implementation cannot save more than that, and it would introduce state that can drift, partial-update failure modes, and a much worse story when something looks wrong. A two-minute idempotent rebuild that you can rerun at any time is a genuinely good trade at 3 M rows.

Keep full recompute recommended

Silver and gold stay .mode("overwrite"). Bronze remains the only incremental layer, which is where incrementality is genuinely hard and already solved by Auto Loader's checkpoint.

  • Idempotent. Rerun any time, get the same answer
  • Self-healing. A restated partition, a bug fix in a transform, or a late correction all just get absorbed by the next run — no backfill logic
  • Explainable. “Gold is a pure function of silver” is one sentence

77 s per run · scales to roughly 20–50 M rows before it hurts

Incremental silver + gold possible

Silver would MERGE per partition label; gold would recompute only the affected months via replaceWhere.

  • Silver must keep the _partition column it currently drops, and replace-by-partition rather than overwrite
  • The catch in gold: a sales partition is a publication week, but the contract dates inside it can land in many different months. So “which months changed?” has to be derived from the batch's data, not its filename — that is the part that quietly gets wrong
  • Real benefit only once a full rebuild stops fitting in a run window

~a day of work · saves ≤77 s per run today

If the goal is the interview rather than the runtime, there is a third path worth naming: rebuild the pipeline as Lakeflow Declarative Pipelines (DLT) with streaming tables and AUTO CDC. It makes incrementality declarative instead of hand-rolled, and it is the most Databricks-native answer to this exact question. It is also a rewrite of all four notebooks, and I have not verified what Free Edition permits here — I would want to prove that with a throwaway pipeline before committing to it. Worth discussing; not worth doing blind.

The cheaper win, if the goal is “I don't want to run it by hand”: add a file arrival trigger to the job so it fires within about a minute of getdata uploading. That removes the manual step entirely without touching the transform design at all — and it is about six lines of YAML.
