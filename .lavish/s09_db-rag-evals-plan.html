the three questions, answered up front

Q1 · “Can I add an LLM-as-a-judge in Databricks like RAGAS?”

Yes — two layers, both buildable today

Parity layer: the dev repo's RAGAS judge is already reusable — same metrics (faithfulness, answer_relevancy, context_precision plus the depth-v2 rubric's five depth metrics). Run it over both agents' answers so scores are directly comparable — one judge, one rubric, two systems.

Native layer: MLflow 3 mlflow.genai.evaluate() with custom @scorer judges running on an FMAPI model (e.g. gpt-oss-120b). Assessments attach to the traces shipped on the rag branch, land in workspace.rag.judge_scores, and get a dashboard page.

evidence: src/evals/judge.py (dev), databricks-mlflow-evaluation skill, live traces on both endpoints

Q2 · “Is the single loop because of the model?”

Mostly no — it's the loop design and prompt. Model is third.

Ranked causes, from reading both implementations:

  1. Structure — Databricks retrieves 8 chunks before the LLM is ever consulted, then asks a yes/no “enough to answer?”. With 8 plausible excerpts, “yes” is nearly always defensible. Dev's LLM starts empty and must drive every retrieval itself via tool calls.
  2. Prompt — dev's system prompt is a research protocol: identify sub-topics, one focused call each, “for a broad question this may be 5–8 calls”. Ours has no protocol, no calibration, and an unparseable reply defaults to “answer”.
  3. Model — dev runs DeepSeek v4; ours llama-3.3-70b at temp 0. Real but secondary — and testable, since this workspace now serves 8 FMAPI chat models.

evidence: AGENTIC_RAG_SYSTEM_PROMPT lines 184–194 (dev) vs decide() in src/lib/rag_agent.py:191

Q3 · “Capture dev answers as goldens and optimise toward them?”

Yes — the dev workbench already persists everything we need

POST /api/ask with setups=["rag_agent"] runs the agentic loop and stores the answer, retrieved contexts and the per-iteration trace (queries, chunk counts) in its history; POST /api/judge scores the entry with RAGAS and stores that too.

Export those entries as a golden_answers entity through the existing landing contract (sha8 parquet → volume → rag_ingest → silver), then score every Databricks variant against them with the same judge until broad questions get dev-like research behaviour.

evidence: /api/ask + /api/judge in dev src/api/main.py; landing contract proven on branch rag

Canonical probe question (goes in the golden set, drives the demo):
“Can you give me a guide into what I need to know about Databricks — I'm interviewing for solution architect.”
Dev today: 5–8 focused retrievals, a Key-Findings answer citing many videos. Databricks today: 1 retrieval, prose answer from whatever the first 8 chunks happened to cover.

Honest caveat: for narrow questions, one hop is often genuinely sufficient — the gte index's first 8 chunks are good. Single-hop is only a defect on broad questions. That's why the golden set is stratified broad/narrow and success is judged per stratum, not globally.

judge design

One judge for parity, one for the platform story

Parity rule: a score is only comparable if the same judge produced it. So the dev repo's RAGAS judge (DeepSeek-backed, rubric depth-v2) scores both agents' answers — run on the laptop via a small bridge script executed with the dev repo's own venv, the exact pattern _chroma_dump.py proved. Nothing leaves the workspace; we pull answers out and judge locally.

metricwhat it measuresdev RAGAS judgedatabricks-native mirror
faithfulnessis every claim supported by retrieved chunks?ragas-v1custom @scorer on FMAPI (or built-in RetrievalGroundedness)
answer_relevancydoes the answer address the question?ragas-v1built-in RelevanceToQuery
context_precisionwere the retrieved chunks useful?ragas-v1custom @scorer per-chunk verdicts
coverage · evidence_breadth · insight_depth · specificity · calibration the depth rubric — rewards multi-source synthesis, the thing single-hop answers can't do depth-v2 (60% of composite)ported as one multi-metric @scorer call
correctness vs goldendoes it agree with the dev reference answer?—built-in Correctness with golden as expectation
hops · unique_videosresearch behaviour — counted, not judgedfrom workbench tracecounted from RETRIEVER spans in MLflow traces
Why depth-v2 matters here: the dev repo added it precisely because ragas-v1 lets a faithful one-chunk restatement score ~1.0. If we optimised on grounding metrics alone, the current single-hop agent would already look fine and nothing would improve. Depth metrics (coverage, evidence breadth) are what make multi-hop research win the eval.

Where scores live: one MLflow run per variant in experiment rag-agent-evals (params: prompt version, model, mode; metrics: judge scores + hops), rows in workspace.rag.judge_scores, and a new page on the existing rag_eval dashboard. Trace assessments make individual answers inspectable in the Traces tab.

optimisation matrix

Variants that isolate prompt from model

Each variant runs the full golden question set through the local agent build (same code path the endpoint serves), gets judged, and becomes one MLflow run. A1-on-llama vs A0-on-gpt-oss isolates whether the prompt or the model moves the needle.

variantchangehypothesis

Success gate: on broad questions — mean hops ≥ 3 (from RETRIEVER spans), depth-v2 composite within 5% of the dev golden composite or better; on narrow questions — no regression vs A0 (single-hop staying single-hop on narrow questions is correct). Winner's config becomes rag_agent.py defaults; agent re-registered and redeployed; final judged run against the live endpoint.
