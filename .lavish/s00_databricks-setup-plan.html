The commands — and where they come from

None of these are Databricks built-ins. They are targets in this repo's own Makefile, written for this project, each a thin wrapper so you never have to remember flags. Under the hood they call one of three things: the Databricks CLI you installed (~/.local/bin/databricks, always invoked as databricks --profile DEFAULT, authed by your OAuth login), the Databricks Python SDK (databricks-sdk, installed into .venv by uv sync), or purely local tools (pytest, ruff) that never touch the workspace. The right column is the literal thing each target runs.

CommandWhenWhat it actually runs
make testAfter any transform change. Local Spark, no workspace, no cost. If this is red, nothing else matters yet.uv run pytest — local only, works with zero Databricks setup
make shipThe inner loop: test → validate → deploy → run, job logs streaming back here. One command from edit to "it ran in Databricks".pytest, then databricks bundle validate / deploy / run — CLI
make syncLeave running while iterating on one notebook; every save appears in the workspace instantly. Files only — job/dashboard changes still need a deploy.databricks sync --watch — CLI (+ jq to resolve your username)
make sql FILE=…Run a local .sql file on the serverless warehouse from the terminal — the scriptable twin of the SQL editor.scripts/run_sql.py via the Python SDK (WorkspaceClient), not the CLI
make pull-dashboardAfter editing the dashboard in the UI, before committing. The repo stays the source of truth.databricks bundle generate dashboard — CLI
make destroyWipe everything the bundle deployed; make ship rebuilds it from zero. This is what makes experiments cheap.databricks bundle destroy — CLI

So: installing the CLI gave you the databricks binary and the OAuth profile; uv sync gave you the SDK and pytest; the Makefile is what composes them into a workflow, and it lives in git like everything else — make help lists every target with its one-line description.

◆ The rule of thumb

Writing logic → here, with tests and Claude. Looking at results → the browser: SQL editor for ad-hoc queries, notebook UI for exploration, dashboard for the end product. The loop exists so that "see it in Databricks" is never more than one make ship away from "edited it locally".

The silver rules come from your dbt project, not from guesswork

The dbt pipeline in data-qa-agent already cleaned exactly this data for Postgres. Silver ports its staging models rule-for-rule — each as a pure function with a local test:

Sales (from stg_sales)

  • contract_dt "20160414.0" → strip ".0" → date; keep only 8-digit, year ≥ 2010
  • postcode "2327.0" → "2327" (stays string)
  • house/unit from strata_no empty-check
  • price must be digits, $10k–$8M — the $10k floor removes non-arms-length family transfers
  • RESIDENCE only, non-blank locality; area H→×10,000 to sqm, then banded

Rent (from stg_rent) + the join

  • ISO date parse; H/T → house, else unit — mirrored vocab so sales↔rent join works
  • bedrooms digit-guarded, banded unknown/0–4/5+; rent > 0
  • yield = ratio of averages (never average of ratios), joined on postcode+type+month, n ≥ 5 both sides, additive legs kept
  • divergence from dbt: silver flags bad rows (_quality reasons) instead of dropping; gold applies the filter — quality dashboard and price dashboard read one table

◆ Definition of done for the slice

① make ship runs the job green. ② In the SQL editor: SELECT * FROM workspace.propertyiq.gold_property_yield WHERE postcode = '2000' returns monthly yields. ③ The dashboard shows median price, median rent, yield by postcode over time, plus a quality panel of flagged-row reasons. ④ make destroy && make ship rebuilds it all — proof the whole thing is code.

05The iteration after: updates-only Parquet feed

The CSVs in the volume are stale legacy exports — fine for proving the slice, wrong as the permanent feed. The upgrade: one new publish databricks command in propertyiq_getdata sends only new or changed partitions as Parquet. Nothing downstream changes except bronze's input path.

The contract

Source already writes 754 immutable weekly sales partitions + 114 rent months, each sha256-manifested. Publish diffs the manifest against a volume listing and uploads what's missing as landing/sales/period=YYYYMMDD_<sha8>.parquet and landing/lodgements/month=YYYY-MM_<sha8>.parquet — zstd, all columns STRING (silver owns typing), no state file: the filename encodes the content, so diff-by-name is diff-by-content.

Why hash-named, append-only files

Rentboard rewrites its trailing month each run — as a new hash-named file, Auto Loader's exactly-once tracking ingests it naturally and silver keeps the newest version per month. The same rule future-proofs sales restatements. One invariant everywhere: landing is append-only; silver resolves versions.

Steady state ≈ 1–2 MB/week. Bootstrap = all 868 partitions, ~150–250 MB of Parquet, one command. Source changes: uv add pyarrow databricks-sdk + ~100-line sink module.

⚑ Two upstream gaps to know about (both fixable in propertyiq_getdata, neither blocks v1)

Restatements: the source discards VG yearly-archive corrections below its watermark — the lake forwards whatever it gets, but can't see what the source never processes. Stale current month: a cached partial rent .xlsx is never re-fetched until deleted by hand. Flagged so "no updates seen" is never mistaken for "no updates exist".

08Risks worth naming

medium

Sales data has two permanent encoding eras

Partitions before 2024 carry pandas float damage (2327.0, 20150416.0); later ones are clean DAT strings — and the damaged years survive nowhere else, so the era-absorbing rules are load-bearing forever. Both eras go in the test fixtures.

medium

Dashboard JSON may need UI repair

The widget-spec schema is only partly documented; the property repoint may need one round of visual fixes. Mitigation unchanged: deploy, fix in UI, make pull-dashboard. Budget 20 minutes.

low

Free Edition fit

Push-based landing needs no egress; ~250 MB Parquet is trivial; job graph stays under 5 concurrent tasks; one 2X-Small warehouse serves SQL editor, dashboard and Genie. Public open data (NSW VG, Rental Bonds, ABS) is compatible with non-commercial terms.

low

CLAUDE.md contradicts this work

The repo rule says "no real data, synthetic only" — written for interview-brief reasons that don't apply to public open datasets. Until reworded (runway step 8), every future session will trip over it.
