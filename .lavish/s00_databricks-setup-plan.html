01What is already on disk

databricks-spike/ is now a git repo with one commit. It is a working medallion pipeline plus the machinery to push it into a workspace. Every design choice in it falls out of a documented Free Edition limit, which makes each one something you can defend out loud.

the trick

Notebooks as plain .py

Files start with # Databricks notebook source and split cells with # COMMAND ----------. Databricks renders them as real notebooks; git sees clean Python.

No conversion step in either direction. This is the whole local↔cloud story.

the discipline

Logic outside the notebooks

Every cleaning rule is a pure function in src/lib/transforms.py with a unit test. Notebooks read a table, call a transform, write a table.

Five-second test loop instead of a four-minute job run — and reviewable as code.

the deliverable

Dashboard as code

An 8-widget AI/BI dashboard lives as .lvdash.json, deployed by the bundle, with a make pull-dashboard round-trip for UI edits.

Edit visually where that is faster; the repo stays the source of truth.

02The decision: code here, or code in Databricks?

This is the question you asked, and the honest answer is that it depends on what is being scored. In two of the four rounds nobody watches you type. In one of them, how you use the platform is the entire test. Pick per round, not once.

A · Everything in Databricks

Use for Round 3 only
What it looks like
  • Notebooks authored in the browser
  • Databricks Assistant generates code
  • Git folder for version control
Why it wins there
  • Round 3 explicitly scores "AI as a partner" on their platform, screen shared
  • Zero setup risk on the day
What it costs
  • No fast test loop, no real diffs
  • Browser editing is slow for anything over ~50 lines
  • Jobs and dashboards must be hand-wired in the UI

B · Everything local

Too rigid on its own
What it looks like
  • Author here, make deploy, read job logs in the terminal
  • Never open the workspace UI
Why it appeals
  • Fast, versioned, agent-drivable
  • Reproducible from a clean workspace
What it costs
  • Dashboards are genuinely painful to build blind in JSON
  • You would never see Genie, lineage or the Assistant — the things that make a demo land
  • In Round 3 it reads as avoiding the platform

C · Hybrid recommended

Default for rounds 2 and 4
What it looks like
  • Logic, notebooks and SQL authored here with Claude
  • make ship pushes and runs; logs stream back
  • Dashboards drafted as code, polished in the UI, pulled back
  • make sync --watch when iterating on one notebook live
Why it wins
  • Terminal speed and a browser you can screen-share
  • Everything is reproducible — you can destroy and rebuild the demo in minutes
  • Round 4 gives you four hours; this is what makes four hours enough
What it costs
  • One-time CLI + auth setup
  • Dashboard round-trip is a habit you must not forget

◆ The rule of thumb

Nobody is watching → work locally. You get tests, diffs and an agent. Someone is watching → work in the browser, with the repo already deployed behind you so you are editing something that exists rather than building from nothing. The worst outcome is screen-sharing a terminal while a panel of Solutions Architects waits to see their own product.

03How well does Claude reach into Databricks?

Better than you might expect, but not through one magic connector. There are three distinct paths and they are useful at different moments. Path 1 is the workhorse and needs no integration work at all.

PathEffortFree EditionWhat Claude can actually do
1 · CLI + Asset Bundles
workhorse		 Already wired works This is the real integration. I run make ship, read the deploy output and the streamed job logs, see the stack trace, fix the notebook, redeploy. A complete write→run→observe→fix loop with no MCP server involved. Everything in Section 05 assumes this and nothing more.
2 · Databricks managed MCP
nice-to-have		 ~20 min PAT only Databricks hosts MCP servers at /api/2.0/mcp/… for Unity Catalog functions, Genie spaces and vector search. Adding one lets me query table metadata and ask Genie questions without you pasting results back. The docs' recommended OAuth route needs the account console, which Free Edition does not have — so use a personal access token.
3 · Databricks Assistant
part of the test		 Zero works Built into the notebook and SQL editor. Not something I drive — but in Round 3 the interviewers want to see you use it, catch it when it hallucinates, and correct it out loud. Treat it as a scored tool, not a convenience.

⚑ The scratchpad trick, straight from their brief

The Round 3 prep notes say: "iterate AI prompts in a separate scratchpad before pasting into the notebook." That scratchpad is this terminal. Ask me here for the PySpark, read it, judge it, then type or paste it into the Databricks notebook and narrate why. That is simultaneously the fastest path and a live demonstration of "you are the pilot" — which is the exact behaviour they say they are scoring.

Adding the MCP server, if you want path 2

# Free Edition has no account console, so OAuth app registration is out.
# Create a PAT: Settings → Developer → Access tokens.

claude mcp add-json databricks-uc '{
  "type": "http",
  "url": "https://<workspace>.cloud.databricks.com/api/2.0/mcp/functions/workspace/retail_spike",
  "headers": { "Authorization": "Bearer <your-pat>" }
}'

# Genie space (once you have created one over the gold tables):
claude mcp add-json databricks-genie '{
  "type": "http",
  "url": "https://<workspace>.cloud.databricks.com/api/2.0/mcp/genie/<space-id>",
  "headers": { "Authorization": "Bearer <your-pat>" }
}'

Worth doing after the pipeline runs, not before. It is a multiplier on an existing setup, not a substitute for one — and it is a nice thing to mention in Round 2 when the topic of agents over governed data comes up.

05Per-round game plan

What this repo is for changes at every stage. In Round 2 it is a memory aid you never open. In Round 4 it is the product.

02

Design & Architecture 60 min 1–2 SAs as stakeholders

mode · nothing shared · repo is rehearsal only

You are not coding. The value of the repo here is that every architectural claim you make is one you have actually implemented, so the follow-up question never catches you out. When they ask why you would not just filter bad rows at ingest, you have a real answer and a real table.

Rehearse three trade-offs out loud, all of which live in the code: bronze keeps everything so silver can be rebuilt; silver flags rather than drops so one table serves both dashboards; gold is pre-aggregated because a 2X-Small warehouse should never scan row-level data for BI.

Their stated #1 criterion is "think out loud." Start with discovery questions, not a diagram. Their listed pitfall is literally "jumping the gun" — building before defining assumptions.
03

Coding / "vibe" pairing 60 min full screen share Free Edition

mode · Databricks-native, this terminal as scratchpad

Work in the Databricks notebook UI. Use the Assistant. Do not run a local deploy loop on camera — it reads as avoiding their product, and the round is explicitly about problem solving with AI tooling on the platform.

Have this repo already deployed before you join. Then a synthetic dataset, a Volume, working transform patterns and a warehouse all exist. When they hand you the data-generation prompt you are adapting a working pipeline, not starting at an empty cell.

The scored behaviour is catching the AI being wrong. Ask the Assistant for something you know it will get slightly off — a window function, or a join that will explode row counts — then say what is wrong and fix it. That single moment is what they are looking for.
04

Build, Demo, Pitch 4 h build 60 min panel 75% customer skills

mode · hybrid, and this is where the repo pays for itself

The prompt lands 24 hours ahead; the build is capped at four hours. Their own breakdown gives only 1.5 hours to the technical build. You cannot spend that hour and a half fighting setup — which is precisely what everything above buys back.

Plan: rename the schema, swap the synthetic generator for whatever vertical the prompt names, adjust the gold aggregates, redeploy, repoint the dashboard. Ninety minutes is comfortable if the scaffold already runs, and impossible if it does not.

Demo the dashboard and Genie, not the notebooks. The panel plays a Business Leader, a CTO and a VP of Engineering. Two of those three do not want to see code. They score the story; the build is explicitly called "a prop", and it "does not all have to work behind the scenes."

07Risks and open questions

Ordered by how much they would hurt if ignored until the day of an interview.

⚠ Your Mac cannot resolve its own user account

id -un returns 501 instead of nathanphillips, and ls -l shows numeric owners. Consequences seen directly: brew install crashes, sudo reports "you do not exist in the passwd database", and Spark dies with a Kerberos login error that has nothing to do with Kerberos. This is macOS DirectoryServices in a bad state — a reboot should clear it. Until then make test cannot run, so the unit tests in this repo are written but unproven. Everything else — the CLI, bundles, deploys, the workspace — is unaffected.

medium

Dashboard JSON may need UI repair

The .lvdash.json widget-spec schema is only partly documented publicly. The file is internally consistent and uses documented widget types, but a spec version could be off.

Mitigation is already in place: deploy, fix visually, make pull-dashboard. Budget 20 minutes the first time, and do it before Round 4, not during it.

medium

OAuth on Free Edition is inconsistent

Community reports disagree on whether databricks auth login completes against a Free Edition host. scripts/auth.sh tries OAuth and falls back to a PAT prompt, so either way you get a working profile.

If you end up on a PAT: it is workspace-scoped and auto-revoked after 90 days of disuse. Fine for this, wrong for anything real — worth saying if asked.

low

Free Edition quotas are tight

One SQL warehouse, one active pipeline per type, 5 concurrent job tasks, apps auto-stop after 24 hours. The repo already fits inside all of these, but a Round 4 prompt asking for streaming plus batch plus an app could bump the ceiling.

LinkedIn verification raises several caps. Do it on day 1, not on the day.

low

Non-commercial, public data only

Free Edition terms are non-commercial, and the interview brief forbids proprietary or confidential data outright. The repo generates everything in-workspace, which also sidesteps the restricted-egress limit.

Two constraints, one design decision. Worth naming explicitly if anyone asks where the data came from.
